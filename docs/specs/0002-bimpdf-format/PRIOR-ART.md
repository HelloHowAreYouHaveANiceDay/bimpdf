# PRIOR-ART: .bim.pdf prior art, self-declaration, and PDF-native mapping

Card B (t_b82f920d), 2026-11-20. Research only. CONTEXT.md decisions 1–5 are taken as given.
Every claim cites a source. **UNVERIFIED** means I could not confirm it from a primary or near-primary source in this pass. Secondary sources (LoC format descriptions, vendor docs, library source code) are labelled as such.

## TL;DR

- **Factur-X is the template.** It uses a fixed attachment filename, a fixed AFRelationship, an XMP namespace with a PDF/A extension-schema block, nested ascending profiles declared in XMP, and an open (Apache-2.0) validator that wraps veraPDF. .bim.pdf should copy that structure nearly one to one.
- **The PDF Association's 2025 app note gives the exact recipe** for a format like ours. Put the manifest in an Associated File with a _custom second-class AFRelationship_ (as C2PA does with `C2PA_Manifest`). Give it a fixed or prefixed filename, an IANA `Subtype`, a `Desc`, and an entry in EmbeddedFiles. Attach the schema with `AFRelationship /Schema`. Keep only small label metadata in XMP. PieceInfo is for closed workflows only, and that is the `.ai` anti-pattern.
- **Registering a prefix is cheap and public.** Open an issue on github.com/adobe/pdf-names-list; the 2026 LGEN request was closed within a day. Publishing the `/Extensions` entry then means filing an issue on github.com/pdf-association/pdf-extensions, which only lists publicly documented extensions under registered prefixes.
- **Viewer reality.** Measure/VP, PageLabels, Outlines, OCGs and attachments are broadly honoured. 3D is weak: Acrobat ships with 3D disabled by default, pdf.js has no 3D, and only Foxit documents glTF support. pdf.js and Acrobat JS can't see AFRelationship. So discovery has to work through filename, `Desc` and XMP, not AFRelationship alone.
- **Conformance target.** Use PDF/A-3b (PDF 1.7) as the archival profile now and plan for PDF/A-4f. PDF/A-4 drops the XMP extension-schema requirement in favour of a RELAX-NG schema attached as an AF.

### 1.5 LibreOffice hybrid PDF

- Writer's "hybrid PDF" option embeds the ODF source; LibreOffice reopens it as editable, while other viewers show the PDF (Tom Forth, 2017, secondary). The TDF wiki FAQ is behind a bot wall and could not be fetched.
- Mechanism: a TDF bug comment says it "appends our source ODF to PDF. It is not attached…", generated as PDF 1.4 (bugs.documentfoundation.org #95328, snippet only). So it is **not** a standard EmbeddedFile/AF. The exact key (believed to be a trailer-level `/AdditionalStreams`) is **UNVERIFIED**.
- Discovery is the failure: "There's no indication in the metadata of the PDF… surprisingly difficult to tell whether a PDF is hybrid in any automated way… LibreOffice the only piece of software… that knows what to do" (Forth).

**Lesson:** a private stream with no XMP label, no attachment-pane entry and no /Extensions entry gives exactly the outcome we must avoid.

### 1.6 Adobe Illustrator `.ai` (closed counter-example)

- Since Illustrator 9 an `.ai` is "a shell of a PDF file. The actual Adobe Illustrator content is stored as 'private data'… not accessed by any standard PDF viewer". It lives in page `/PieceInfo /Illustrator /Private`, split across `AIPrivateData1..K` blocks (Adobe community, Adobe staff answer; reverse-engineered format notes at github goncalveslucasv/ai-file FORMAT.md).
- Synchronization risk: the PDF part can be edited in Acrobat without the native data changing. Validity depends on PieceInfo `LastModified` matching (printplanet forum, Adobe staff).
- The PDF Association: PieceInfo "is appropriate only for private metadata used within closed workflows… not recommended for intentional preservation"; it is invisible to PDF JavaScript and viewers (Including custom metadata, 2025, p.9–10).

**Lesson:** nothing bim-semantic goes in PieceInfo. Use `LastModified`-style staleness detection, but via a hash of the page content in the manifest, not via PieceInfo.

## 2. Self-declaration and discovery

### 2.1 XMP custom namespaces and the PDF/A extension schema

- PDF/A-1/2/3 **require** every custom XMP property to be described by an embedded extension-schema block (`pdfaExtension:schemas` → `pdfaSchema:namespaceURI/prefix/property` → `pdfaProperty:name/valueType/category/description`). Container prefixes are _required_, not just preferred. (TN0009, pdfa.org; PDFlib KB)
- pdfa.org publishes free templates (ExtensionSchemaAllSubsets-2025_02.xml, a TDMRep template, a PDF Declarations template) and says the requirement holds "always". (pdfa.org/resource/xmp-extension-schema-templates)
- **PDF/A-4 drops it**: it "should" include a RELAX-NG schema (ISO 16684-2) as an Associated File with `AFRelationship /Schema`, Subtype application/xml or text/xml (ISO 19005-4 §6.7, per pdfa.org templates page and the 2025 app note).
- Precedent for an AI-oriented XMP namespace: LLMind LRFS v1.0 (2026-04) binds `llmind` → `https://llmind.org/ns/1.0/`, with a versioned namespace URI ("Breaking changes will use /ns/2.0/"). It is a single-vendor spec; adoption is **UNVERIFIED**. (llmind.org/spec)

**Implication:** today's `http://pdfbim.com/ns/1.0/` (`pdfbim:version`, generator) has no extension-schema block, so any PDF/A claim fails. Keep reading it, and write a new versioned namespace that resolves to the spec, plus the extension-schema block, plus (for 4f) a RELAX-NG AF.

### 2.2 Developer prefixes and `/Extensions`

- Second-class names use a registered prefix (ISO 32000-2 Annex E). Registry: github.com/adobe/pdf-names-list. Open "a new Issue, filling out the template"; one prefix per issue; entries go into a public XLSX. Example: LGEN was requested 2026-05-12 and closed as completed 2026-05-13. (repo README; issue #56)
- `/Extensions` catalog dictionary (ISO 32000-2 §7.12, Table 49): per prefix, a DeveloperExtensions dict, or **an array of them in PDF 2.0**, with `BaseVersion` (req.), `ExtensionLevel` (int, req.), `URL`, `ExtensionRevision`. (pdfa.org/how-to-get-started-with-pdf-2-0; pdf-issues #732)
- Open TWG issue #732 (Feb 2026) proposes making `ExtensionLevel` optional and `URL` the definition URL. It is not settled; for now `ExtensionLevel` is required. The "monotonically increasing" rule was relaxed to a recommendation (#239).
- Public listing: github.com/pdf-association/pdf-extensions (CC-BY-4.0, created 2026-03) feeds pdfa.org/extensions. Add one "via a new Issue"; it lists "only publicly documented extension information using publicly registered developer prefixes".
- Whether a bim-related prefix is already taken: **UNVERIFIED** (check the XLSX before filing).

### 2.3 AF / AFRelationship (PDF20_AN002)

- Associated Files (ISO 32000-2 §14.13) originated in PDF/A-3 (2012). They can attach to the catalog, pages, XObjects, annotations, structure elements and marked content (via `/Properties … /MCAF`). Required: an `/AF` entry on the object plus `AFRelationship` on the filespec. Values: `Source, Data, Alternative, Supplement, EncryptedPayload, FormData, Schema, Unspecified`; **"Custom values may be used where none of these entries is appropriate."** (PDF20_AN002, 2018; pdfa.org LogicalStructureObjects cheat sheet)
- PDF 2.0 adds an optional filespec `/Thumb`; pdfa.org encourages viewers to show AFRelationship in attachment panes. (how-to-get-started-with-pdf-2-0)

### 2.4 "Including custom metadata structures in PDF" (PDF Association, 2025-10, CC-BY-4.0)

This is the most directly applicable source. Key rules, verbatim or close:

- XMP is "the preferred method" for _small_ payloads. Large manifests (JSON/YAML) go in **Associated Files**, listed in EmbeddedFiles "to maximise their discoverability".
- Manifests should: use "a dedicated 2nd-class name" for AFRelationship (e.g. C2PA's `C2PA_Manifest`); use "a fixed filename (such as factur-x.xml)" **or** a registered-prefix filename prefix plus a known extension; set an IANA media type (no params) in `Subtype`.
- Its figure shows a catalog AF with `ACME_xxxx.json`, `AFRelationship ACME_Manifest`, `Subtype application/json`, a `Desc`, and a nested `/AF` holding the schema (`AFRelationship Schema`, `application/schema+json`). For PDF/A-4 the schema rides as AF of the manifest's filespec.
- Viewers rarely show AFRelationship, and **PDF JavaScript cannot read it** (`this.dataObjects` exposes name, description, MIME, size). So use a known filename plus `Desc`.
- AF in PDF/A is limited to PDF/A-3 (1.7) and PDF/A-4f/4e (2.0).
- In encrypted PDFs, AF payloads are always encrypted; there is no equivalent of `EncryptMetadata` for AF.
- PieceInfo: closed workflows only. Info dict: "largely deprecated in PDF 2.0". Custom structure attributes (owner `NSO` or a second-class name) and structure-attribute UserProperties are valid for per-element data.

### 2.5 PDF 2.0 Info-dictionary deprecation

ISO 32000-2 deprecates the Info dictionary except `CreationDate` and `ModDate`; XMP equivalents exist for all keys (PDF Association forensics talk 2025, slide "Deprecated in 2.0"; 2025 app note p.10). So nothing bim-specific goes in Info. A short human hint there is harmless but not normative.

## 4. Recommendations for .bim.pdf (ranked)

1. **Adopt the Factur-X pattern wholesale.** Use a fixed manifest filename (e.g. `bim-pdf.json`), an XMP label namespace, nested profiles, per-profile JSON Schema, and one CLI validator (veraPDF + schema). This is the most-proven precedent and the cheapest to explain.
2. **Register a developer prefix now** (adobe/pdf-names-list issue). Use it for (a) the custom AFRelationship name (`<PFX>_Manifest`, as C2PA does), (b) sidecar filename prefixes, (c) any second-class keys and structure-attribute owner. Then file an issue on pdf-association/pdf-extensions with the bimpdf.com/spec URL.
3. **Manifest as a catalog Associated File, per the 2025 app note.** Fixed filename, AFRelationship `<PFX>_Manifest`, `Subtype application/json`, a human `Desc` (how-to-read hint), listed in EmbeddedFiles, with its JSON Schema nested as AF `AFRelationship /Schema` `application/schema+json`. Sidecars: AF on the object they describe (page/annotation/structure element), plus EmbeddedFiles, plus a `Desc`; use standard AFRelationship values (`Data`, `Supplement`, `Source`) where they fit.
4. **PDF-native first for visible semantics.** Scales via `/VP` + `/Measure` (fills a gap Revit's exporter leaves); sheet numbers via `/PageLabels`; index via `/Outlines`; categories/levels via OCGs; markups as annotations with document-unique `/NM`. The manifest _references_ these, never duplicates them as truth.
5. **Conformance-profile model (nested, Factur-X style):**
   - `core`: valid PDF + XMP label + manifest AF. Every producer must emit it.
   - `drawing`: core + VP/Measure, PageLabels, Outlines, OCGs.
   - `linked`: drawing + element↔geometry links (structure attributes or per-object AF) + sidecars.
   - `3d`: linked + glTF (AF fallback; ISO/TS 32007 RichMedia optional), opt-in only.
   - Orthogonal archival flag: `pdfa3b` now, `pdfa4f` later. Declared in XMP (`profile`, `archival`) and in the manifest. Readers state the minimum profile they accept.
6. **Discovery stack (cheapest first, each layer independent):**
   1. visible notice page/stamp (shipped);
   2. XMP label in a new versioned namespace resolving to bimpdf.com/spec (`formatVersion`, `profile`, `manifest` filename, `specURL`, `readingHint`), plus the PDF/A extension-schema block. Keep reading legacy `pdfbim:` (`http://pdfbim.com/ns/1.0/`);
   3. catalog `/Extensions /<PFX>` with `BaseVersion`, `ExtensionLevel`, `URL`;
   4. AF with custom AFRelationship + fixed filename + `Desc` on every attachment (the filename+Desc layer is what pdf.js and Acrobat JS can see);
   5. `README-agent.md` as AF (`Supplement`, text/markdown), a short how-to-read for agents;
   6. bimpdf.com/llms.txt plus `rel="describedby"` from spec pages (llms.txt v2).
7. **Never use PieceInfo or private streams** for bim data (the `.ai` and LibreOffice-hybrid failure modes). For staleness, store a hash of each page's content stream in the manifest.
8. **3D off by default**, poster always present, glTF as a plain AF first. Viewer support doesn't justify more today.
9. **Validator:** Apache-2.0 CLI that runs veraPDF (for PDF/A claims) plus JSON Schema plus profile rules. Publish test files and a hosted check on bimpdf.com, as Mustang and buildingSMART do.
10. **Versioning:** IFC-style Major.Minor.Addendum.Corrigendum semantics; namespace URI and `ExtensionLevel` change only on Major (LRFS `/ns/2.0/` model).
